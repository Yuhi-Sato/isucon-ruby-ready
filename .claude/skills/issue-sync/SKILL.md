# Issueによる作業共有

## 前提: この運用はAIが自律的に回す

手動でのissue更新・確認は人間には負荷が高いため、ここで定めるタイミングでAIが自発的にissueを読み書きする。issueの起票・追記・クローズはすべてAIが行い、人間はissueを手動更新しない。

人間がすることは2つだけ: ①施策の方向付け（何に着手するかを決める）、②トリガー1で競合が出た時の最終判断（詳細はトリガー1）。

## 起票粒度: エンドポイント単位

**目的**: 施策の競合検知は「同じ対象に複数人が同時に手を入れていないか」を見るためのものなので、比較の単位が揃っている必要がある。エンドポイントは3人の間で粒度の認識が揃えやすい単位のため、これを基本単位にする。

**What/How**:
- 1エンドポイント = 1 issue。タイトルは対象エンドポイント（例: `GET /api/chairs`）
- 単一のエンドポイントに紐づかない施策（DB全体設定、ミドルウェア設定、複数エンドポイントにまたがる変更など）は例外とし、施策名をタイトルにする

**Few-shot**:
- 良: `GET /api/chairs` という1エンドポイントの高速化 → 専用issue
- 良: MySQLのバッファプールサイズ変更（特定エンドポイントに紐づかない） → 例外issue「MySQL: innodb_buffer_pool_size調整」
- 悪: 「パフォーマンス改善デイ1」のような日付・作業セッション単位でissueを作る（粒度が人によって揺れ、競合検知の比較ができない）

## issue本文の構成

**目的**: 読者（他の2人＋AI）がissueを開いた時点で、チャット履歴なしに「何のために・何を・何をしない前提で」取り組んでいるかを復元できるようにする。

**What/How**: 本文は次の3項目のみ。

- **意図**: 何が問題で、どうなれば良いのか（1〜2行）
- **やること**: 着手時点で想定している変更の範囲
- **やらないこと**: 意図的にスコープ外とした対象（隣接エンドポイント、関連しそうだが今回は触らない箇所など）

過程（どう調査してこの結論に至ったか）は書かない。着手後に想定が変わったら、この3項目を書き直す（追記で積まない）。

**Few-shot**:
- 良:
  ```
  ## 意図
  GET /api/chairs が全件走査で応答が遅い。indexを足して絞り込みを速くする。

  ## やること
  webapp/sql の chairs テーブルに index を追加する。

  ## やらないこと
  GET /api/chairs/:id は対象に含めない（別issueで管理）。
  ```
- 悪: 「調査した結果A案とB案があってB案にした」と経緯を書く

## トリガー1: ブランチを切る前に競合を検知する

**目的**: 同じエンドポイントに複数人が同時に着手すると、後からマージするPRが手戻りになる。ブランチを切る前という最も手戻りコストが低いタイミングで検知する。

**What/How**:
1. [branch-pr-workflow](../branch-pr-workflow/SKILL.md) の手順でブランチ名（対象施策）を決めたら、ブランチを切る前に `gh issue list --state open` で対象エンドポイントのissueが既に開いていないか確認する
2. 開いているissueが見つかったら、**ブランチを切らずに止めて**ユーザに提示する（担当者・issue URL）。続行するかはユーザが判断する
3. 見つからなければ、上記「issue本文の構成」に従って新規issueを起票してからブランチを切る

**Few-shot**:
- 良: `u-ktk/chairs-index` を切る前に `GET /api/chairs` の未クローズissueが無いことを確認し、issueを起票してからブランチを切る
- 悪: issueを確認せずブランチを切り、後から別の人が同じエンドポイントに手を入れていたと分かる

## トリガー2: PRを作る時にissueへリンクする

**目的**: 「今どのエンドポイントが誰の作業中か」をissue単体で判断できるように、進行中の実体（PR）をissueから辿れるようにする。

**What/How**: [create-pr](../create-pr/SKILL.md) の手順でPRを作成したら、同じ作業の中で対応issueにPRのURLをコメント追記する。

**Few-shot**:
- 良: PR作成直後に `gh issue comment <issue番号> --body "PR: <url>"` を実行する
- 悪: issueへのリンクをPR作成時に付けず、後から手動で追う

## トリガー3: PRがマージされたらissueをクローズする

**目的**: 完了した作業をissue一覧に残すと、開いているissue＝進行中という前提が崩れ、読者が都度中身を確認しないと現状を判断できなくなる。

**What/How**: PRがmainにマージされたら、同じタイミングで対応issueをクローズする。

**Few-shot**:
- 良: マージ確認後 `gh issue close <issue番号>` を実行する
- 悪: PRはマージ済みだがissueが開いたままで、他の2人が「まだ進行中」と誤認する
