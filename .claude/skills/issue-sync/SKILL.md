# Issueによる作業共有

## 前提: この運用はAIが自律的に回す

手動でのissue更新・確認は人間には負荷が高いため、ここで定めるタイミングでAIが自発的にissueを読み書きする。issueの追記・クローズはAIが行い、人間はissueを手動更新しない。

## 役割分担

起票とクローズは分析担当（u-ktk）、実装は実装担当（Yuhi-Sato / garebareDA）が受け持つ（`roles/after-initial.md`）。

- 起票: 分析担当が、mainの計測結果を分析したあとに行う（下記「起票粒度」「issue本文の構成」に従う）。実装担当は自分で起票しない
- 実装: 実装担当は、割り当てられたissueを解決するPRを作る
- クローズ: 分析担当が、マージ後にmainでベンチを回してスコアを確認してから行う（トリガー3）

人間がすることは2つだけ: ①施策の方向付け（何に着手するかを決める）、②トリガー1で割り当てに問題があった時の最終判断（詳細はトリガー1）。

## 起票粒度: エンドポイント単位

**目的**: 施策の競合検知は「同じ対象に複数人が同時に手を入れていないか」を見るためのものなので、比較の単位が揃っている必要がある。エンドポイントは3人の間で粒度の認識が揃えやすい単位のため、これを基本単位にする。

**What/How**:
- 1エンドポイント = 1 issue
- タイトルは「why + what（対象エンドポイントなど）」の形で書く。エンドポイント名だけだと、他の施策と区別できず競合に見えるし、何のための変更かも分からない
- 単一のエンドポイントに紐づかない施策（DB全体設定、ミドルウェア設定、複数エンドポイントにまたがる変更など）は例外とし、施策名をタイトルにする

**Few-shot**:
- 良: `GET /api/isu/:jia_isu_uuid/graph: 対象日の行だけ取得し、1秒タイムアウトを減らす`
- 悪: `GET /api/isu/:jia_isu_uuid/graph`（エンドポイントだけだと他の施策と競合しうる＆なんのためかわからない）
- 良: MySQLのバッファプールサイズ変更（特定エンドポイントに紐づかない） → 例外issue「MySQL: innodb_buffer_pool_size調整」

## issue本文の構成

**目的**: 読者（他の2人＋AI）がissueを開いた時点で、チャット履歴なしに「何のために・何を・何をしない前提で」取り組んでいるかを復元できるようにする。

**What/How**: 本文は次の3項目のみ。

- **意図**: 何が問題で、どうなれば良いのか（1〜2行）
- **やること**: 着手時点で想定している変更の範囲
- **やらないこと**: 意図的にスコープ外とした対象（隣接エンドポイント、関連しそうだが今回は触らない箇所など）

過程（どう調査してこの結論に至ったか）は書かない。着手後に想定が変わったら、この3項目を書き直す（追記で積まない）。

**Few-shot**:
- 良:
  ```
  ## 意図
  GET /api/chairs が全件走査で応答が遅い。indexを足して絞り込みを速くする。

  ## やること
  webapp/sql の chairs テーブルに index を追加する。

  ## やらないこと
  GET /api/chairs/:id は対象に含めない（別issueで管理）。
  ```
- 悪: 「調査した結果A案とB案があってB案にした」と経緯を書く

## トリガー1: ブランチを切る前に競合を検知する

**目的**: 同じエンドポイントに複数人が同時に着手すると、後からマージするPRが手戻りになる。ブランチを切る前という最も手戻りコストが低いタイミングで、「自分に割り当てられたissueだけを解決する」状態になっているかを確認する。

**What/How**:
1. [branch-pr-workflow](../branch-pr-workflow/SKILL.md) の手順でブランチ名（対象施策）を決めたら、ブランチを切る前に `gh issue list --state open` で対象エンドポイントのissueを確認する
2. 対象のissueが自分に割り当てられていて、同じエンドポイントを対象にした他のissueやPRが開いていなければ、ブランチを切る
3. 次のどれかなら、**ブランチを切らずに止めて**ユーザに提示する（担当者・issue URL）。続行するかはユーザが判断する
   - 対象のissueが存在しない（実装担当は自分で起票しない。分析担当に起票を依頼する）
   - 対象のissueが他の人に割り当てられている
   - 同じエンドポイントを対象にした別のissueやPRが開いている

**Few-shot**:
- 良: `u-ktk` が起票した `GET /api/chairs` のissueが自分に割り当てられていることを確認し、`yuhi-sato/chairs-index` を切る
- 悪: 対象のissueが無いまま、自分でissueを起票してブランチを切る
- 悪: issueを確認せずブランチを切り、後から別の人が同じエンドポイントに手を入れていたと分かる

## トリガー2: PRを作る時にissueへリンクする

**目的**: 「今どのエンドポイントが誰の作業中か」をissue単体で判断できるように、進行中の実体（PR）をissueから辿れるようにする。

**What/How**: [create-pr](../create-pr/SKILL.md) の手順でPRを作成したら、同じ作業の中で対応issueにPRのURLをコメント追記する。

**Few-shot**:
- 良: PR作成直後に `gh issue comment <issue番号> --body "PR: <url>"` を実行する
- 悪: issueへのリンクをPR作成時に付けず、後から手動で追う

## トリガー3: PRがマージされたらissueをクローズする

**目的**: 完了した作業をissue一覧に残すと、開いているissue＝進行中という前提が崩れ、読者が都度中身を確認しないと現状を判断できなくなる。一方で、マージしただけではスコアが上がったか分からないため、クローズは効果の確認後に行う。

**What/How**: 分析担当が、PRがmainにマージされたらmainでベンチを回し、スコアをissueにコメントする。スコアが上がっていればissueをクローズする。下がった・変わらないときはクローズせず、issueに書いて切り戻しを検討する。

**Few-shot**:
- 良: マージ後にmainでベンチを回し、スコアをissueに書いてから `gh issue close <issue番号>` を実行する
- 悪: PRをマージした時点でスコアを見ずにissueをクローズし、効果がなかったことが埋もれる
