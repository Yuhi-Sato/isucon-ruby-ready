## 本文構成

**目的**: 人・AIのレビュアーがPR本文だけで、何のために・どこを・どう変えて・結果は何かを判断できるようにする。毎回この順で書けば、PRごとに読み方を変えずに済む。

**What/How**:
- 見出しは 意図 → 対象 → 変更 → 実測値 の順に書き、最後に「マージ条件」を置く（書き方は下の各節）
- 材料は `git diff <base>...HEAD`・コミットログ・ユーザが渡した情報（形式は問わない）から集める
- 材料から埋められない項目は推測せずユーザに聞く。ただし実測値だけは聞かず「未計測」でよい
- 経緯・却下案は書かない

### 意図

**目的**: 変更の妥当性は、何のための変更かが分からないと判断できない。

**What/How**: 何が問題で、どうなれば良いのかを1〜2行で書く。

**Few-shot**:
- 悪: 「高速化」
- 良: 「rides を chair_id で全走査しているため、indexを足して絞り込みを速くする」

### 対象

**目的**: サーバが3台に分かれているため、どの役に効く変更かが分からないと影響範囲を読めない。

**What/How**: サーバ役（s1〜s3）と、変更したファイルを書く。

**Few-shot**:
- 悪: 「アプリ」
- 良: 「s1（アプリ役）の `webapp/sql/1-schema.sql`」

### 変更

**目的**: 具体値で書けば、差分を開かなくても何が変わったかを追える。

**What/How**: ファイルパス・設定キー・コマンドなど、具体的な値で書く。

**Few-shot**:
- 悪: 「indexを追加した」
- 良: 「`webapp/sql/1-schema.sql` に `ALTER TABLE rides ADD INDEX idx_chair_id (chair_id)` を追加」

### 実測値

**目的**: 効果の有無は数値でしか判断できず、推測の断言は判断を誤らせる。

**What/How**: before/afterを生の数値で書く。無ければ「未計測」。数値を捏造しない。

**Few-shot**:
- 悪: 「効果があったと思われる」
- 良: 「スコア 1200 → 1850（整合性PASS）」、または「未計測」

## マージ条件

**目的**: 本文の内容とは別に、いつマージしてよいかの判断が要る。レビュアーがチェック項目だけでマージ可否を判定できるようにする。

**What/How**:
- **通常**: ベンチを回し、スコアが上がり、整合性チェックがPASSしたらマージ
  - 本文: `- [ ] ベンチのスコアが上がった` `- [ ] 整合性チェックがPASS`
- **軽い設定**: ベンチを省略してマージOK。判定の4条件は [branch-pr-workflow](../branch-pr-workflow/SKILL.md) の「軽い設定の判定条件」
  - 本文: `- [ ] 軽い設定の4条件を満たす（ベンチ省略）` と、満たす根拠を1行

## 作成手順

**目的**: 外に出る操作（push・PR作成）は取り消しづらい。本文を見せて承認を得てから実行する。

**What/How**:
1. 本文案を出す → 修正があれば反映して再提示
2. 承認後、`git push -u origin HEAD`
3. 本文を一時ファイルに書いて作成する。baseは `main`
   ```bash
   gh pr create --base main --head "$(git branch --show-current)" \
     --title "<変更の意図を短く>" --body-file "$BODY"
   ```
4. 一時ファイルを削除し、PRのURLを返す
5. [issue-sync](../issue-sync/SKILL.md) の「トリガー2」に従い、対応issueにPRのURLを追記する
- 422 は push 漏れを疑い、push してから再実行する。`gh` 未ログインなら `gh auth login` を案内する

**Few-shot**:
- 良: 本文案を見せて承認を得てから、push と `gh pr create` を実行する
- 悪: 承認前に push する
