# ブランチとPRの運用

## ブランチ: 施策ごとにスコアを比較でき、悪化したら切り戻せる状態を保つ

ISUCONは時間勝負で、施策ごとのスコアを比べて次の一手を決める。比較が成り立たないと、効いた施策と効かなかった施策の区別がつかず、次の一手を誤る。ベンチは時間がかかるので、回す価値のある施策に絞って試行回数を稼ぐ。

### 環境構築はmain直

- `make setup-sN` が作る `chore: setup (sN)` のcommitはmainに直接pushする
- 環境構築が終わった後の変更（アプリ・SQL・設定）は、次のブランチで行う

**Few-shot**:
- 良: `make setup-s2` の commit を main に push する
- 悪: スキーマにindexを足す変更を、環境構築のついでにmainへ直接commitする

### 試作ブランチの切り方と命名

- ブランチを切る前に [issue-sync](../issue-sync/SKILL.md) の「トリガー1」に従い、対象エンドポイントの競合を確認する
- 名前は `<GitHubユーザ名>/<施策名>`。施策名は英小文字とハイフン
- 番号は付けない。施策の番号は PR 番号だけにする
- main から切る、コミットする、テストを実行する、は `CLAUDE.md` の原則に従う

**Few-shot**:
- 良: `u-ktk/users-index`
- 悪: `fix` `test2`（誰の何の施策か分からない）
- 悪: `u-ktk/03-users-index`（連番が PR 番号とずれる）

### ベンチの実行手順

1. ローカルで `git push origin <ブランチ名>`
2. ローカルから対象サーバーへ反映する
   - ベンチ直前の準備（サーバーで pull、ログ削除、設定反映、DB・nginx を含む全再起動。ベンチ自体は実行しない）: `make remote-bench-prep-s1 BRANCH=<ブランチ名>`
   - アプリコードだけ軽く反映する: `make remote-deploy-s1 BRANCH=<ブランチ名>`
   - s2 / s3 も同じ形。全台は `make remote-deploy-all BRANCH=<ブランチ名>`
3. ベンチ実行サーバーからベンチを実行する。設定・DB・nginx を変えたときは、実行前に必ず 2 の `bench-prep` を済ませる

**Few-shot**:
- 良: `make remote-bench-prep-s1 BRANCH=u-ktk/users-index` のあとにベンチ
- 悪: サーバー上のブランチを確認せずにベンチを叩く

### 軽い設定の判定条件

- 次を**すべて**満たすものだけ「軽い設定」とする
  1. アプリコードの処理・返す値を変えない（設定・DBスキーマ・計測用の追加だけで完結する）
  2. `POST /initialize` の後でも同じ状態になる（初期化処理に組み込み済み）
  3. 設定行の削除だけで元に戻せる
  4. 結果の並び順など、暗黙にindexや設定へ依存する挙動が無い
- 判定に迷ったら通常（ベンチを回す）。軽い設定の扱いはチームで確認して確定する（**暫定運用**）
- PR本文にどう書くかは [create-pr](../create-pr/SKILL.md) の「マージ条件」

**Few-shot**:
- 良: 初期化処理にALTERを足したインデックス追加 → 軽い設定（4条件を満たす。返す行は同じ）
- 良: nginxのログ形式の変更 → 軽い設定（計測用で、アプリの処理に触れない）
- 悪: 手でALTERしただけのインデックスを軽い設定にする（条件2: 初期化で消える）
- 悪: N+1解消を軽い設定にする（条件1: アプリの処理を変える。キャッシュ・bulk insertも同じ）

## PR: 今このブランチに何が入っているかを、読者が一目で取れる状態を保つ

PRは、レビュアーと将来の自分が「いま何が入っていて、何が効いたか」を判断する材料。読み取れないと、判断が古い情報や過程のノイズの上で行われる。

### PRは create-pr の手順で作る

- PRを作る・既存PRの本文を直すときは、先に [create-pr](../create-pr/SKILL.md) を読み、その本文構成・マージ条件・作成手順に沿う
- 以降の2節は、create-pr に足す運用だけを書く

**Few-shot**:
- 良: 「PR作って」と言われたら create-pr を読み、本文案を見せて承認を得てから作る
- 悪: このスキルの記述だけを頼りに `gh pr create` を叩く（本文構成やマージ条件を落とす）

### PR本文と現状図の更新

- 変更を足したら、その場でPR本文を今の状態に書き直す。前の版の記述を残さない
- サーバ構成・通信経路を変えたら、同じタイミングで [architecture スキルの現状図](../architecture/SKILL.md) を直す
- 効果が出なかった施策も、そのコードを消すまでは本文の実測値に残す

**Few-shot**:
- 良: DBを別サーバへ移した時点で、PR本文の「変更」と現状図のMySQLの位置を両方直す
- 悪: 「最初はA案だったがB案に変えた」と本文に経緯を積む

### PRタイトルの書き方

`<何をした>ことで<何を狙う>` の形で書く。どちらか一方にしない。

**Few-shot**:
- 良: `MySQLをisucon14-2へ移し、椅子の位置更新の応答を縮める`
- 悪: `bind-addressを0.0.0.0にする`（Whatだけ。何のためか分からない）
- 悪: `応答を速くする`（意図だけ。何をしたか分からない）
