# ISUCON スコア戦略（マニュアル × ベンチマーカーの走行結果）

## 概要

ISUCONのスコアは「速いほど高い」ではなく、**マニュアルに書かれた計算式**で決まる。加点される操作・減点されるエラー・失格条件・負荷が上がる条件は問題ごとに違い、ここを読まずに遅い箇所から潰すと「速くなったのに点が伸びない」「エラー減点で相殺」「失格で0点」になる。

本スキルは次の2つの入力を突き合わせ、**スコア式のどの項を動かすか**という観点で改善案を出す。

| 入力 | 中身 | 置き場所 |
|---|---|---|
| 問題マニュアル | レギュレーション、アプリケーションマニュアル、スコア計算式 | `docs/manual.md`（競技開始時に1回コミット） |
| ベンチGUIログ | ポータルに表示されたスコア・結果（pass/fail）・エラー/警告メッセージ・ベンチマーカーの標準出力 | `docs/bench/<日時>-<ブランチ>-<ハッシュ>.md`（ベンチごとに`make bench-done`で保存） |
| alpの集計（補助） | エンドポイントごとの件数・合計時間・平均・p99 | `measure-logs/alp/<日時>-<サーバー>-<ブランチ>-<ハッシュ>.log`（`make bench-done` がサーバーで集計・commitしたものを取り込む） |

alpは**手順3で「動かす項」が決まったあと**に、その項に関わるエンドポイントがどれだけ遅い・多いかを引くためだけに読む（提案に「どのエンドポイントか」を書けるようにするため）。alpから先に読んで遅い順に直そうとしない。MySQLログ（`make slow-query`）・プロファイラは**本スキルでは読まない**。それらは「なぜ遅いか」を調べる別作業で、本スキルは「何が点になるか」から逆算して、直すべき規則・シナリオを決めるところまでを担当する。

鉄則（CLAUDE.md）: 推測するな。計測せよ。提案には必ず「マニュアルの該当箇所」と「ベンチログの該当行」を根拠として添える。根拠を示せない案は出さない。

## 対応範囲

**本スキルの担当は分析と提案まで。** コード変更・設定変更・デプロイ・ベンチ実行は行わない（書き込むのは `docs/` のベンチログ・スコアモデル・分析だけ）。提案が採用されたら、実装は通常の作業（必要ならisucon-ruby-testingで回帰テスト、isucon-vernier-profilingでCPU計測）に引き継ぐ。

## 手順0: 入力を揃える

1. `docs/manual.md` があるか確認する。無ければユーザーにマニュアルの本文を貼ってもらう（ポータルは認証付きのことが多くURLからは取れない）か、配布リポジトリ内のマニュアル（`docs/` `manual/` `*.md`）を探して`docs/manual.md`にコピーする。**マニュアル無しでは本スキルを進めない**（スコア式が分からないと提案の根拠が作れない）
2. `docs/score-model.md` があるか確認する。無ければ手順1で作る。あれば「改訂」欄を見て、マニュアルの更新（競技中に追記されることがある）が反映されているか確認する
3. 直近のベンチログを揃える。ユーザーが「ベンチ終わった」と合図してポータルの内容をチャットに貼った場合は、**一字も変えずに**一時ファイルへ書き、`make bench-done` で保存してから読む（保存しないと後でスコア推移が追えない）

   ```bash
   # ベンチを回したブランチをcheckoutした状態で実行する（ファイル名のブランチ・コミットが「そのベンチで動いていたコード」になる）
   git rev-parse --abbrev-ref HEAD
   mkdir -p tmp
   cat > tmp/bench-result.txt <<'BENCH'
   <ユーザーが貼った結果をそのまま>
   BENCH
   make bench-done < tmp/bench-result.txt
   ```

   `make bench-done` は次をまとめて行う（`scripts/bench-done.sh`）: `docs/bench/YYYYMMDD-HHMMSS-<ブランチ>-<コミット>.md` に保存してcommit → 全サーバーで alp / slow-query を集計してDiscordに通知し `measure-logs/` をcommit・push（`make remote-nd-all`）→ `git pull --rebase` で取り込み → push。
   人が手元で回す場合は `pbpaste | make bench-done`（macOS）/ `make bench-done < result.txt`
4. SSHがサーバーに届かない環境（Claude Code on the web など）では `make bench-done` が `remote-nd-all` を警告付きでスキップする。その場合は**ユーザーに手元で `make remote-nd-all` を実行してもらい**、完了の返事を待ってから `git pull --rebase` で `measure-logs/` を取り込む。推測で代替しない

## 手順1: マニュアルからスコアモデルを作る（初回・マニュアル改訂時のみ）

マニュアル全文を読み、[references/score-model-template.md](references/score-model-template.md) の形式で `docs/score-model.md` に要約する。以後のベンチ分析はマニュアル本文ではなくこのファイルを読む（毎回全文を読むと時間を溶かす）。

抜き出す項目（詳細はテンプレート参照）:

- **スコア式**: 何を数えて何倍するか。加点対象の操作と重み
- **減点・失格**: エラー1件あたりの減点、エラー数の上限、タイムアウト秒数、整合性チェックの内容
- **負荷の駆動ループ**: ベンチマーカーがどう負荷を増やすか（「レスポンスが速いとユーザーが増える」「特定の操作が成功すると次のシナリオに進む」など）。ここが**スコアの上限を決める**
- **制約**: 初期化（`/initialize`）の制限時間、レスポンスの許容誤差、キャッシュ可否、外部サービス呼び出しの制約
- **提出要件**: 再起動試験、使ってよいサーバー台数など（isucon-final-checkで使う）

マニュアルの記述を**原文のまま引用**して残す。要約の言い換えで条件を取り違えるのが最も多い事故。

## 手順2: ベンチログを分類して読む

ベンチログの各行を次の5種に分類する。分類できない行は「不明」として残し、推測で埋めない。

| 分類 | 例 | 見るポイント |
|---|---|---|
| 結果 | `pass` / `fail` / `失格` | failなら**スコアの議論はしない**。failの原因行だけを扱う |
| スコア | 総合スコア、加点・減点の内訳、レベル/ステージ、走行中に定期的に出る内訳の行（評価点の分布・満足度条件ごとの達成数など） | 内訳があれば式のどの項が小さいかが直接分かる。走行中に定期的に出る行は、**どの時点で伸びが止まったか**を見る |
| エラー | `タイムアウト`、`レスポンスが不正`、`整合性`、`初期化に失敗`、HTTP 5xx | **エラーの種類ごとに件数を数える**。メッセージに含まれるパス・メソッドでエンドポイントを特定する |
| ヒント | `89.7%のライドは椅子がマッチされるまでの時間、92.3%のライドはマッチされた椅子が乗車地点までに掛かる時間、53.2%のライドは椅子の実移動時間に不満がありました` | ベンチマーカーが「マニュアルのどの満足度条件を満たせていないか」を直接教えている行。**条件ごとに分解し、マニュアルの該当条項（閾値・スコアへの影響）と対応づける**。未達率が高い条件ほど優先。**ヒント行がマニュアルの全条件を網羅しているとは限らない**ので、内訳の行と突き合わせる |
| 負荷の推移 | `負荷レベルが上がりました`、`ユーザーが離脱`、`シナリオNに到達`、ユーザー数・並列数 | 駆動ループが回っているか止まっているか。止まった直前のエラー/遅延が本命 |
| 環境・その他 | 初期化にかかった時間、ベンチ走行時間、ベンチマーカーのバージョン | 初期化時間が制限に近ければそれ自体が改善対象 |

エラー件数の数え方（ログ保存後にローカルで数える）:

1. まず結果行に**ベンチマーカー自身の集計**が無いか探す（例: ISUCON14 の `結果 pass=true スコア=26381 種別エラー数="map[1:24 17:2]"`）。あればそれが正で、自前で数えない
2. 無ければ警告・エラーの行を数える。時刻やIDは潰すが、**エラーコードは残す**（数字を一律に潰すと `CODE=1` と `CODE=17` が同じ種類になる）

```bash
# 例: 時刻を落とし、CODE=<n> 以外の数字を潰して種類別に数える（sed には後読みが無いため perl を使う）
grep -E 'level=(WARN|ERROR)|エラー|error|失敗|タイムアウト|timeout' docs/bench/<最新>.md \
  | perl -pe 's/^time=\S+ //; s/(?<!CODE=)\b\d+/N/g' \
  | sort | uniq -c | sort -rn | head -20
```

問題ごとの抽出コマンド（エラーの集計、内訳行の取り出し）が決まったら、`docs/score-model.md` の「ログの読み方」節に書き残す。毎回コマンドを組み直さずに済む。

**前回ベンチとの比較**（必須）: `docs/bench/` の直前のログと、最終時点の内訳・エラー件数・負荷の推移（ユーザー数・離脱数など）を表にして並べる。スコアの差だけでは、どの項が効いてどの項が悪化したかが分からない。前回より改善した項と悪化した項が両方ある場合、悪化した項がスコアの伸びを削っている本命であることが多い。

## 手順3: スコア式に当てはめて「動かす項」を決める

`docs/score-model.md` のスコア式と手順2の分類を突き合わせ、次の順で判定する。**上の判定が該当したら下には進まない**（複数同時に直そうとして検証できなくなるのを防ぐ）。

1. **失格・failしている** → 原因行の修正が唯一の課題。速度改善は0点のまま
2. **減点がスコアに対して無視できない**（目安: 減点が総合スコアの1割超、またはエラー数が失格上限の半分超） → エラー種類の上位から潰す。マニュアルで減点額が大きいエラーを優先する
3. **駆動ループが止まっている**（負荷レベルが上がらない、ユーザーが離脱している、シナリオが先に進まない） → ループの条件（マニュアル記載）を満たしていない箇所。多くはタイムアウト閾値ぎりぎりのエンドポイントや、特定操作の失敗。ここが解けると**スコアの上限が上がる**ので、単発の高速化より効く
4. **加点の重みに偏りがある**（例: 操作Aは1件10点、操作Bは1件1点） → 重みの大きい操作を成功させている件数を増やす。マニュアルとルート定義から、重い操作がどのエンドポイント群で構成されるかを特定する
5. **上記いずれも該当しない（規則上の未達がなく純粋なスループット勝負）** → 本スキルの範囲外。alpの `sum` 上位3エンドポイントを挙げたうえで「規則上の未達なし。計測（slow-query / Vernier）に進む」と結論して終える

各判定で「どの数値が根拠か」を必ず書く。例: 「エラー内訳: タイムアウト 143件（減点 1件5点=715点、総合スコア 4,200点の17%） → 判定2」。減点方式でない問題（エラーが上限件数でFAILになるだけの問題）では、判定2の根拠を「上限に対する割合」と「前回からの増減」で書く。件数が上限の半分未満でも、前回から倍増しているなら判定4以降の案の中で扱う。

**判定3・4でエンドポイント群が決まったら alp を引く。** 分析対象のベンチと同じコミットの `measure-logs/alp/` の最新ログ（サーバーごとに1本。nginxが動くサーバーのものを使う）から、その項に関わるエンドポイントの `count` / `sum` / `avg` / `p99` を抜き出し、提案の根拠に添える。

```bash
ls -t measure-logs/alp/*-<コミット>.log | head    # ヘッダー行（# commit:）でベンチと同じコミットか確認する
grep -vE '^(#|\+)' measure-logs/alp/<ファイル> | head -25       # ヘッダー行と罫線を除いて上位を見る（sum降順。tool-config/alp/config.yml の sort: sum）
```

alpで見るのは「動かす項に関わるエンドポイントが**どれだけ遅い・多いか**」まで。タイムアウト閾値（マニュアル）と `p99` を比べれば、判定3の「閾値ぎりぎりのエンドポイント」を名指しできる。**なぜ遅いか**（クエリ・N+1・CPU）は slow-query / プロファイラの別作業で、本スキルでは断定しない。alpに該当エンドポイントが無い（`matching_groups` 未設定で潰れている）場合は、`isucon-measurement-setup` で設定を直すことを提案に添える。

## 手順3.5: 着手中の施策と突き合わせる

提案を書く前に、チームがすでに着手している施策を確認する。同じ施策を別の案として出すと作業が重複し、「前回の変更は効いたか」の判定も根拠を欠く。

```bash
gh issue list --state open
gh pr list --state open
gh pr list --state merged --limit 5   # 直前のベンチまでに入った変更
```

- 手順3で決めた「動かす項」に対応する issue や PR が**着手中**なら、新しい案にはしない。推奨案を「その PR を仕上げてベンチにかける」とし、PR 番号を書く
- 前回から今回のベンチの間にマージされた PR に、**検証条件**（「次のベンチで○○が△△になる」）が書かれていれば、手順4のスコア推移ではそれと照らし合わせて「効いた／効いていない」を判定する

## 手順4: 提案をまとめる

[references/proposal-template.md](references/proposal-template.md) の形式で、**最大3案・推奨1案**にまとめてユーザーに提示する。各案に必ず含めるもの:

- **根拠**: マニュアルの引用（該当条項）とベンチログの該当行（件数・スコア）
- **動かす項**: スコア式のどの項がどう変わる見込みか。桁で良いので見積もりを書く（「タイムアウト143件がゼロになれば減点715点が消え、かつ負荷レベルが1段上がる可能性」）
- **手段の概要**: 何をどこで直すか（実装の詳細は書かない。方針レベル）
- **検証方法**: 次のベンチログで**どの行がどう変わっていれば成功か**。これが書けない案は根拠が弱い
- **リスク**: 失格条件・整合性チェック・提出要件に触れないか。マニュアルの該当条項を引く

提案の後に、`docs/bench/` の過去ログと比較したスコア推移を1行添える（「前回 3,800 → 今回 4,200。前回の変更（コミットxxx）は効いている/効いていない」）。前回の変更が効いていないなら、その変更の巻き戻しも候補に入れる。

提示した分析は `docs/strategy/<分析したベンチログと同じファイル名>.md` に保存してコミットする。ファイル名を揃えるのは、どのベンチの分析かを名前で引けるようにするため。冒頭には、分析したベンチログ・比較した前回のログ・`docs/score-model.md` へのリンクを書く。保存しないと、手順5の答え合わせで「何を予想していたか」が残っていない。

## 手順5: 次のベンチで答え合わせをする

提案が実装されベンチが回ったら、手順0-3で新しいログを保存する。次に `docs/strategy/` の直前の分析を開き、そこに書いた「検証方法」の行が予想どおり変わったかを**最初に**確認する。予想と違うなら、スコアモデル（手順1）の読み違いを疑い、マニュアルの原文に戻る。

## やらないこと

- マニュアルを読まずにベンチログだけで提案する（スコア式なしの提案は推測）
- failしているベンチのログで速度改善を提案する
- alpを「動かす項」が決まる前に読んで遅い順に直そうとすること。MySQLログ・プロファイラを読むこと、および「たぶんN+1」「たぶんインデックス」のような原因の断定。原因調査は別作業
- 3案を超える提案の羅列。優先順位を付けられないなら判定（手順3）に戻る

## よくある失敗

| 失敗 | 対策 |
|---|---|
| 遅いエンドポイントを直したがスコアが変わらない | そのエンドポイントは加点対象か、駆動ループに関与しているかをスコアモデルで確認する。点にならない処理は後回し |
| ヒント行を「全体的に遅い」と丸めて読む | 条件ごとに分解する。例の行なら「マッチングまでの時間」と「乗車地点到着まで」が9割超で、「実移動時間」は5割。前2つはマッチング処理の規則、後者は別の規則 |
| ヒント行だけを見て優先度を決める | ヒント行は満足度条件の一部しか出さないことがある（ISUCON14 では4条件のうち3つだけ）。走行中の内訳の行で、ヒント行に出ない条件の達成率も確認する |
| スコアの差だけ見て「前回の変更が効いた」と判断する | 手順2の前回比較表で項ごとに見る。ある項が改善しても、別の項の悪化で伸びが削られていることがある |
| 分析を会話にだけ残し、次のベンチで何を確認すべきか分からなくなる | 手順4の最後で `docs/strategy/` に保存してコミットする |
| エラー減点を無視して高速化を続け、負荷が上がった分エラーも増えて相殺 | 手順3の判定2を先に通す。負荷が上がるとタイムアウト件数も増えるので、閾値ぎりぎりの処理を先に潰す |
| 「タイムアウト」をアプリの遅さと決めつける | マニュアルのタイムアウト定義（接続/レスポンス/シナリオ全体）を確認する。初期化タイムアウトやベンチ側の並列数制限のこともある |
| マニュアルの要約を言い換えて条件を取り違える | `docs/score-model.md` には原文を引用して残す。判断に迷ったら原文に戻る |
| ベンチログを保存せず、どの変更で上がった/下がったか分からなくなる | 手順0の`make bench-done`をベンチごとに実施する（ベンチを回したブランチで。保存・commit・pushまで行う） |
| alpの遅い順に提案して、点にならないエンドポイントを直す | alpは手順3で項が決まってから、その項のエンドポイントだけを引く |
| 競技中にマニュアルが改訂され、古いスコアモデルで判断し続ける | ポータルの更新告知を見たら手順1をやり直し、`docs/score-model.md` の改訂欄に日時を書く |
| 一度に複数の案を実装して、どれが効いたか分からない | 推奨1案だけ実装し、ベンチで検証してから次へ進む |
