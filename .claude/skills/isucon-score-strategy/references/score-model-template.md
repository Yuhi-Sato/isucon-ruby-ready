# スコアモデルのテンプレート（`docs/score-model.md`）

マニュアルから抜き出したスコアに関わる記述を、この形式で `docs/score-model.md` にまとめる。
**各項目はマニュアルの原文を引用して書く。** 言い換えは条件の取り違えを生む。該当する記述が無い項目は「記載なし」と書き、空欄にしない（後で「読み落とし」と「記載なし」を区別するため）。

```markdown
# スコアモデル

- 問題名:
- マニュアルの取得元: （ポータルURL / 配布リポジトリ内パス）
- 作成日時:
- 改訂: （マニュアル改訂を反映した日時を追記していく。例: 2026-09-20 14:05 レギュレーション改訂v2を反映）

## 1. スコア式

> （原文引用）例: スコア = 成功した注文の合計金額 − エラー数 × 100

- 加点対象の操作と重み:
  | 操作 | 重み | 対応するエンドポイント（マニュアル/コードから特定） |
  |---|---|---|
  |  |  |  |
- 内訳がベンチGUIに表示されるか: （はい / いいえ。表示される場合はその項目名）

## 2. 減点・失格

> （原文引用）例: リクエストの失敗1件につき100点減点。失敗が100件を超えた場合は失格

- エラー1件あたりの減点:
- エラー数の上限（失格条件）:
- タイムアウト秒数と対象（接続 / レスポンス / シナリオ全体）:
- 整合性チェックの内容（何が食い違うとfailか）:
- その他の失格条件（レギュレーション違反、再起動後の起動失敗、初期化失敗など）:

## 3. 負荷の駆動ループ

> （原文引用）例: レスポンスが1秒以内に返り続けると、ベンチマーカーは同時接続ユーザー数を増やします

- 負荷が上がる条件:
- 負荷が下がる / ユーザーが離脱する条件:
- シナリオの段階（レベル・ステージ）と、次に進む条件:
- **スコアの上限を決めているもの**（上記から導く1〜2行の結論）:

## 4. 制約

- 初期化（/initialize 等）の制限時間:
- レスポンスの許容誤差（件数・順序・タイムスタンプなど）:
- キャッシュ・静的配信の可否（マニュアルに明記があれば）:
- 外部サービス呼び出し（決済API等）の制約:
- その他（画像サイズ、データの永続化要件など）:

## 5. 提出要件（isucon-final-check で使う）

- 再起動試験の有無:
- 使用可能なサーバー台数・申告方法:
- 提出締切・最終ベンチの扱い:

## 6. 未確認・不明点

- （マニュアルに記述が無く、ベンチログや動作から確かめる必要があるもの）
```

## 書くときの注意

- 「1. スコア式」の重み表は、加点操作をアプリのエンドポイントに対応づけるところまで書く。`grep -nE "^\s*(get|post|put|delete|patch) " webapp/ruby/*.rb` でルート一覧を出して突き合わせる。ここが埋まっていないと、走行結果のエラー行やヒント行を点に換算できない
- 「3. 負荷の駆動ループ」が最重要。ISUCONのスコアは多くの場合「ベンチマーカーがどれだけ負荷を上げてくれたか」で上限が決まる。マニュアルにループの記述が無い場合は「記載なし」とし、ベンチログの負荷推移（レベル・ユーザー数）の行から観察して「6. 未確認」に仮説として書く
- マニュアルが複数ページ（レギュレーション + アプリケーションマニュアル）に分かれていても、スコアモデルは1ファイルにまとめる
