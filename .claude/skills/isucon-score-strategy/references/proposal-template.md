# 提案のテンプレート

ベンチログ分析の結論はこの形式でユーザーに提示する。**最大3案・推奨1案。** 根拠の欄が空になる案は出さない。

```markdown
## ベンチ分析: <ベンチログのファイル名>

### 現状

- 結果: pass / fail（failなら原因行を引用）
- スコア: <総合>（内訳があれば: 加点 <x> / 減点 <y>）
- スコア推移: 前回 <a>（コミット <hash>）→ 今回 <b>。前回の変更は 効いた / 効いていない / 判断不能（理由）
- エラー内訳（種類別件数、上位3種）:
  | エラー | 件数 | 減点換算 | 主なエンドポイント |
  |---|---|---|---|
  |  |  |  |  |
- 負荷の推移: （レベル・ユーザー数がどこまで上がったか。止まった時点と直前の事象）
- 判定（手順3）: <1〜5のどれか> — 根拠となる数値: <…>

### 推奨案: <一言>

- 根拠（マニュアル）: > 原文引用（docs/score-model.md の該当節）
- 根拠（ベンチログ）: > 該当行の引用（件数・スコア）
- 動かす項: スコア式の <項> が <どう> 変わる見込み（桁の見積もり）
- 手段の概要: （方針レベル。どのエンドポイント/処理をどうするか）
- 検証方法: 次のベンチログで <どの行> が <どう> なっていれば成功
- リスク: （失格条件・整合性チェック・提出要件との関係。マニュアルの該当条項）

### 代替案A: <一言>
（同じ項目。推奨案より優先度が低い理由を1行）

### 代替案B: <一言>
（同上）

### 保留（今回は手を付けない）
- （エラー件数は多いが減点が小さい、等の理由で見送ったものを1行ずつ。後で拾えるように残す）
```

## 書くときの注意

- 「動かす項」の見積もりは桁で良い。ただし**どの項が動くか**は必ず明示する（「速くなる」は項ではない）
- 「検証方法」は走行結果の行（ヒント行の割合・エラー件数・スコア内訳）で書く。走行結果で検証できない案は、スコアに直結する根拠が弱いので推奨案にしない
- 判定1（fail）のときは推奨案のみを出し、代替案は書かない。failの原因が複数あるなら、それぞれを推奨案の中に列挙する
- 「保留」は必ず書く。見送った理由を残しておかないと、次のベンチで同じ検討を繰り返す
