# 後半戦の役割

`after-initial.md`のサイクルを回し、u-ktkが起票するissueが足りなくなったら後半戦に入る。後半戦では、garebareDAが実装から離れてCPUのサンプルプロファイリングを担当する。

| 担当 | GitHub | 役割 |
| --- | --- | --- |
| u-ktk | [u-ktk](https://github.com/u-ktk) | 初動以降と同じ。プロファイル結果も分析に取り込み、issueを作成する。スコアを確認する |
| Yuhi-Sato | [Yuhi-Sato](https://github.com/Yuhi-Sato) | 初動以降と同じ。issueを解決するPRを作成する |
| garebareDA | [garebareDA](https://github.com/garebareDA) | 実装（PR作成）から離れ、CPUのサンプルプロファイリングを取得・解析して結果をu-ktkに渡す |

## 後半戦に入る条件

- [ ] 割り当て可能な未着手issueがなくなった（u-ktkの計測結果の分析から、新しく直すべき対象が見つからなくなった）
- [ ] u-ktkが後半戦に入ることを宣言し、garebareDAに伝えた
- [ ] garebareDAが担当中のissue・PRを片付けた（マージ済み、またはYuhi-Satoかu-ktkに引き継いだ）

alp / slow-queryで見えるボトルネックが出尽くした状態が目安。ここから先はアプリのCPU時間の内訳（どのメソッドが時間を食っているか）を見ないと、次の施策が見つからない。

## サイクル

```
[garebareDA] ベンチ中のアプリのCPUをサンプリング
   ↓
[garebareDA] 結果を解析し、CPU時間の大きい箇所を特定
   ↓
[garebareDA → u-ktk] 結果を共有（保存先とトップの箇所）
   ↓
[u-ktk] プロファイルとalp / slow-queryを突き合わせ、issueを作成
   ↓
[Yuhi-Sato] issueを担当し、PRを作成（以降は after-initial.md と同じ）
   ↓
 mainにマージ → [u-ktk] スコア確認
   ↓
 (最初に戻る。改善後のプロファイルを取り直す)
```

---

## garebareDA

### プロファイリング

- [ ] mainの最新を対象サーバーに反映する（`branch-pr-workflow`）。プロファイルは、評価したいコードが動いている状態で取る
- [ ] サンプリングプロファイラ（Rubyなら`stackprof` / `rbspy`など）を用意する。未導入ならこのときに入れる
- [ ] ベンチを回している間にアプリプロセスをサンプリングする
  - ベンチ開始と同時に取り始め、負荷が乗っている時間帯を対象にする
  - プロファイラ自体の負荷でスコアが変わるため、**プロファイル取得中のスコアは評価に使わない**。スコア確認用のベンチは別に回す
- [ ] 取得したプロファイルを保存する（ファイル名にコミットSHAと日時を入れ、どのコードの結果か分かるようにする）

### 解析と共有

- [ ] CPU時間の大きい順に、メソッド / 行 / 呼び出し元を洗い出す
- [ ] 上位の箇所を、どのエンドポイントから呼ばれているかに対応づける（alpの結果と照らす）
- [ ] 共有メモに「上位N件 / 対応するエンドポイント / 想定される原因」を書き、u-ktkに渡す
  - 推測で原因を断定しない。計測できた数値（サンプル数・割合）を添える
  - 改善案を思いついたら書いてよいが、issueにするかはu-ktkが決める
- [ ] 改善PRのマージ後は、プロファイルを取り直して効果と次の上位を確認する

### やらないこと

- 実装・PR作成（Yuhi-Satoとu-ktkのサイクルに任せる）
- 自分でissueを起票する（起票はu-ktkの役割）
- プロファイル取得中のベンチ結果でスコアを判断する
